## 1. Название и краткое описание

**Vippi Leads** (рабочее название, финальное — TBD) — B2B SaaS для застройщиков и агентств недвижимости Ташкента, который фиксирует каждую входящую заявку из любого канала, запускает таймер первого ответа, напоминает менеджеру о просрочке и показывает владельцу и РОПу, сколько заявок осталось без реакции, у кого и из какого источника. AI готовит краткую сводку заявки, оценку приоритета и черновик ответа на русском или узбекском, который менеджер всегда проверяет сам.

**Позиционирование (CONFIRMED, ADR-004):** двойное — (а) **слой контроля поверх существующей CRM** (amoCRM/Bitrix24): заявки поступают через intake API и импорт CSV, CRM остаётся у клиента, нативная интеграция — в roadmap; (б) **самостоятельный инструмент** для компаний без CRM: единый список заявок с таймером и контролем. В обоих случаях продукт не является CRM: нет воронки, сделок и задач — только контроль реакции на заявки.

**Честное ограничение MVP (CONFIRMED, ADR-017):** время первого ответа фиксируется ручной отметкой менеджера («Отметить первый контакт» / «Отметить черновик отправленным»), а не измеряется автоматически в канале связи.

**Формат текущей версии:** демо-MVP за 7 дней (CONFIRMED) для портфолио, конкурсов и инвесторов. Продажи и оплата — вне MVP.

## 9. Ценностное предложение

**Для собственника:** «Покажем, сколько заявок за период остались без ответа дольше 15 минут, у какого менеджера и из какого источника — по вашим же данным».
**Для РОПа:** список «Без реакции» в реальном времени и уведомления о просрочке.
**Для менеджера:** все заявки в одном списке, таймер и готовый черновик ответа на RU/UZ.

**По подсегментам (CONFIRMED позиционирование, ADR-004):**

| | (а) Компания с CRM | (б) Компания без CRM |
|---|---|---|
| Сообщение | «Не меняйте CRM — добавьте слой контроля: каждая заявка с таймером и отчёт о просрочках» | «Простой список всех заявок с таймером и контролем — без внедрения CRM» |
| Как заявки попадают в систему (MVP) | Intake API (вебхук/форма сайта), CSV-выгрузка из CRM | Ручной ввод менеджером, intake API с сайта, CSV из Excel |
| Чем отличается от конкурентов | От Zukko — не заменяем CRM; от ROPai/Reveo/nilu — все каналы, а не только звонки | От amoCRM/Bitrix24 — без внедрения и обучения, фокус только на реакции |
| Ограничение MVP | Нет нативной интеграции (roadmap); статус ведётся в двух местах; первый ответ — ручная отметка | Первый ответ — ручная отметка |

Эффект (сокращение времени ответа, рост конверсии) — HYPOTHESIS (H-08); ценность каждого подсегмента — HYPOTHESIS (H-06).

## 20. Требования к AI

Принципы (CONFIRMED): таймеры, статусы, права и метрики — обычный код, не LLM. AI только помогает человеку; ничего не отправляет клиентам; текст заявки — недоверенный ввод. Демо — только синтетические данные.

| ID | Требование |
|---|---|
| AI-001 | **Сводка и извлечение.** Вход: источник, текст обращения, имя (без телефона), язык интерфейса. Выход (Zod-схема): `summary` (≤400 символов, на языке интерфейса), `language` (`ru`/`uz`/`mixed`/`unknown`), `need` (≤200), `budget` (`{amount, currency: UZS/USD}` или null), `district` (из справочника 12 районов Ташкента или null), `propertyType` (`APARTMENT`/`HOUSE`/`COMMERCIAL`/`LAND`/`OTHER`/null), `rooms` (1–10 или null), `missingInfo` (до 5 пунктов). Значения, отсутствующие в тексте, — null (запрет «додумывания» в промпте и проверка: число бюджета должно встречаться в тексте). |
| AI-002 | **Оценка вероятности сделки.** `score` 0–100, `band` (`HOT` ≥70, `WARM` 40–69, `COLD` <40 — вычисляется кодом из `score`), `reasons` 2–4 пункта (≤150 символов), `nextQuestions` до 3. В UI — подпись «Оценка — подсказка, а не прогноз». Не влияет на SLA, права и сортировку по умолчанию. |
| AI-003 | **Черновик ответа.** Вход: данные лида, результат AI-001 (если есть), язык (`ru`/`uz`), тон (`FORMAL`/`FRIENDLY`), название компании, имя менеджера. Выход: `text` (≤700 символов), `language`. Узбекский — латиница, обращение на «Siz». Запрещено: обещать цены/скидки/сроки, которых нет во входных данных; ссылки; просьбы о платеже. Пост-проверка кодом: длина, отсутствие URL, язык по алфавиту (кириллица для `uz` → невалидно). Всегда показывается как редактируемый черновик с баннером «Проверьте перед отправкой». |
| AI-004 | **Сводка за неделю для РОПа.** Вход — только агрегаты (KPI FR-051, таблицы FR-052/053 с именами менеджеров и источниками, без данных клиентов). Выход: 3–6 пунктов (≤200 символов) на языке интерфейса; каждое число в тексте должно присутствовать во входных агрегатах (проверка кодом, иначе fallback). |
| AI-005 | **Провайдер (CONFIRMED, ADR-010).** В MVP реализован только Google Gemini: `AI_PROVIDER=gemini`, `AI_MODEL`, `GEMINI_API_KEY`. Без ключа (`AI_PROVIDER=none` или пустой ключ) — режим `rule_based`. Код работает через интерфейс провайдера, чтобы позже добавить OpenAI/Anthropic без изменения AI-модуля (вне MVP). Перед обработкой реальных данных клиентов — юридическая проверка трансграничной передачи в Google (§22). |
| AI-006 | **Fallback.** Используется при: нет ключа; `aiExternalProcessingEnabled=false`; превышен дневной лимит; вход длиннее лимита; таймаут; ошибка провайдера после 1 повтора; ответ не прошёл Zod-валидацию или пост-проверку. Правила fallback детерминированы и описаны в SPEC (раздел 17.6). Результат помечается (FR-073). |
| AI-007 | **Лимиты и кэш.** Таймаут 15 с; 1 повтор только при сетевой ошибке/5xx/429; вход ≤4000 символов текста обращения; ≤200 AI-запросов и ≤300 000 токенов на организацию в сутки (по `Asia/Tashkent`, настраивается env); ≤30 запросов в час на пользователя; кэш по хэшу входа + версии промпта + параметрам. Fallback-результаты не кэшируются. |
| AI-008 | **Безопасность.** Текст заявки передаётся внутри разделителей как данные; системный промпт запрещает выполнять инструкции из данных; у модели нет инструментов/функций; ответ — только JSON по схеме; вывод отображается как простой текст (без HTML/Markdown-рендера). |
| AI-009 | **Наблюдаемость и качество.** Для каждого вызова сохраняются провайдер, модель, версия промпта, флаг и причина fallback, задержка, токены, хэш входа — без текста заявки в логах. Набор оценки: 30 синтетических заявок (RU/UZ/смешанные) с эталонными полями; цель — ≥80% правильно извлечённых полей (HYPOTHESIS); черновики UZ — оценка носителем (H-09). |

## 27. Пользовательские истории и критерии приёмки

Формат AC: «Дано / Когда / Тогда». Все AC автоматизируются тестами, если не указано «ручная проверка».

### US-001. Регистрация организации (owner) — FR-001
*Как владелец, я хочу зарегистрировать компанию, чтобы начать контролировать заявки.*
- **AC-001.** Дано: валидные данные. Когда: отправляю форму. Тогда: созданы организация (`Asia/Tashkent`, AI выключен), пользователь `owner`, SLA-политика 15 мин; я авторизован и вижу пустой список лидов с действиями «Добавить лид», «Импорт CSV», «Пригласить команду».
- **AC-002.** Дано: email уже зарегистрирован. Тогда: 409 `EMAIL_TAKEN`, ошибка у поля email, организация не создана.
- **AC-003.** Дано: пароль короче 10 символов. Тогда: ошибка валидации на клиенте и 400 `VALIDATION_FAILED` на сервере при обходе клиента.

### US-002. Вход и выход — FR-002, FR-003, SEC-003, SEC-004
- **AC-004.** Верные данные → cookie сессии с `HttpOnly`; `GET /auth/me` возвращает пользователя, роль и организацию.
- **AC-005.** Неверный пароль или неизвестный email → одинаковый ответ 401 `INVALID_CREDENTIALS`.
- **AC-006.** 6-я неудачная попытка для одного email за 15 минут → 429 `RATE_LIMITED` с `Retry-After`; событие в аудите.
- **AC-007.** После выхода любой запрос с прежней cookie → 401.

### US-003. Приглашение участников — FR-005, FR-007
- **AC-008.** Owner приглашает email с ролью `head_of_sales` → ссылка показана один раз, срок 7 дней, приглашение в списке ожидающих.
- **AC-009.** Head_of_sales пытается пригласить `head_of_sales` → 403 `FORBIDDEN`; в UI выбор роли ограничен `manager`.
- **AC-010.** Manager не видит раздел приглашений; `POST /invitations` → 403.
- **AC-011.** Повторное приглашение того же email при активном приглашении → 409 `INVITATION_EXISTS`.

### US-004. Принятие приглашения — FR-006
- **AC-012.** Валидная ссылка → видны организация и роль; после ввода имени и пароля создан пользователь с ролью из приглашения, я авторизован.
- **AC-013.** Истёкшая, отозванная или использованная ссылка → экран «Приглашение недействительно» без формы; API 410 `INVITATION_INVALID`.
- **AC-014.** Email приглашения уже зарегистрирован → 409 `EMAIL_TAKEN` с подсказкой обратиться к владельцу.

### US-005. Управление командой — FR-008
- **AC-015.** Owner меняет роль manager → head_of_sales; следующий запрос этого пользователя выполняется с новыми правами.
- **AC-016.** Owner деактивирует менеджера после подтверждения → его сессии недействительны (401), его открытые лиды стали неназначенными с событием в истории, SLA-дедлайны не изменились.
- **AC-017.** Owner не может деактивировать себя или сменить свою роль (кнопки нет; API → 422 `CANNOT_MODIFY_SELF`).

### US-006. Создание лида — FR-010, FR-011, FR-032
- **AC-018.** Без имени и без телефона → ошибка «Укажите имя или телефон»; телефон `90 123-45-67` сохраняется как `+998901234567`; `12345` → ошибка валидации.
- **AC-019.** Созданный лид: `status=NEW`, `slaState=PENDING`, `firstResponseDueAt = receivedAt + 15 мин` (рабочие часы выключены); лид первым в списке.
- **AC-020.** Есть открытый лид с тем же телефоном за 30 дней → новый лид создан с меткой «Возможный дубль» и ссылкой на исходный.

### US-007. Список лидов — FR-017, FR-018
- **AC-021.** Комбинация фильтров работает как «И»; состояние в URL; после перезагрузки фильтры сохранены.
- **AC-022.** Поиск `901234567` находит `+998 90 123 45 67`; поиск `Mirzo Ulug'bek` находит `Mirzo Ulugʻbek`.
- **AC-023.** Manager видит только свои и неназначенные; запрос чужого лида по ID → 404 `NOT_FOUND`.
- **AC-024.** По умолчанию 25 строк, максимум 100; отображается общее количество.

### US-008. Первый контакт и статусы — FR-013, FR-014, FR-035
- **AC-025.** «Отметить первый контакт» с каналом → `firstResponseAt` = серверное время, статус CONTACTED, `slaState=MET`, если до дедлайна, иначе `BREACHED`; событие в истории; лид исчез из «Без реакции».
- **AC-026.** Запрещённый переход (например, NEW→WON) → 422 `INVALID_STATUS_TRANSITION`; в UI такой вариант не предлагается.
- **AC-027.** LOST без причины → 400; NEW→LOST с причиной `SPAM` до дедлайна → `slaState=EXEMPT`; после просрочки — остаётся `BREACHED`.
- **AC-028.** Переоткрытие WON/LOST → CONTACTED доступно owner/head_of_sales; manager → 403.

### US-009. Комментарии и история — FR-015, FR-016
- **AC-029.** Комментарий 1–2000 символов появляется в истории с автором и временем в `Asia/Tashkent`; 2001 символ → ошибка валидации.
- **AC-030.** История — от новых к старым; системные события подписаны «Система».

### US-010. Уведомление о просрочке — FR-033, FR-040, FR-041
- **AC-031.** Лид без контакта: через ≤90 с после дедлайна `slaState=BREACHED`, событие в истории, уведомления ответственному и всем активным head_of_sales; счётчик колокольчика обновился ≤30 с.
- **AC-032.** Двойной запуск задачи (или два экземпляра API) → ровно одно уведомление каждому получателю по лиду.
- **AC-033.** Неназначенный лид → уведомления только head_of_sales (или owner, если head_of_sales нет).
- **AC-034.** Клик по уведомлению открывает лид и помечает уведомление прочитанным; «Прочитать все» обнуляет счётчик.

### US-011. Список «Без реакции» — FR-034, FR-012
- **AC-035.** В списке только `BREACHED` без первого контакта, сортировка по длительности просрочки, колонка «Просрочено на».
- **AC-036.** Head_of_sales переназначает лид из списка → новый ответственный получает `LEAD_ASSIGNED`; дедлайн не изменился.
- **AC-037.** Manager видит в списке только свои и неназначенные лиды.

### US-012. AI-анализ лида — FR-070, FR-073, AI-001, AI-002, AI-006
- **AC-038.** Провайдер настроен, AI включён в организации → ≤15 с: сводка, поля, оценка, причины; метка «AI · {провайдер}/{модель}».
- **AC-039.** Ключа нет → результат по правилам ≤1 с с меткой «Без AI · по правилам» и причиной «AI-провайдер не настроен»; в результате нет слова «AI» и иконки AI.
- **AC-040.** Таймаут или невалидный JSON от провайдера → fallback с соответствующей причиной; в логах нет текста заявки.
- **AC-041.** Повторный запрос без изменения лида → результат из кэша без вызова провайдера (проверяется моком), показано время генерации.

### US-013. Черновик ответа — FR-071, FR-072, AI-003
- **AC-042.** Выбор UZ и «официальный» → черновик латиницей ≤700 символов в редактируемом поле с баннером «Проверьте перед отправкой».
- **AC-043.** «Отметить как отправленный» с каналом при отсутствии первого контакта → первый контакт по правилам AC-025 и событие с признаком `edited`.
- **AC-044.** В API нет эндпоинта, отправляющего сообщения клиентам (проверка по OpenAPI-спецификации).
- **AC-045.** Поле «Бюджет» из AI применяется к лиду только после «Применить»; событие в истории с источником `AI` или `RULES`.

### US-014. Дашборд — FR-050…FR-055
- **AC-046.** На эталонном наборе данных (фикстура с известными ответами) все KPI совпадают с ожидаемыми значениями.
- **AC-047.** Пресет «Сегодня» в 00:30 по Ташкенту включает лиды с 00:00 по Ташкенту (при `TZ=UTC` на сервере).
- **AC-048.** Клик по строке менеджера открывает список лидов с фильтром по менеджеру и периоду.
- **AC-049.** Manager открывает `/dashboard` → экран «Нет доступа»; API → 403.
- **AC-050.** Пустой период → нули и «—» для медианы, сообщение «Нет данных за период», без ошибок.

### US-015. AI-сводка за неделю — FR-074, AI-004
- **AC-051.** Head_of_sales нажимает «Сформировать сводку» → 3–6 пунктов на языке интерфейса; в запросе к провайдеру нет имён/телефонов клиентов (проверка моком); при недоступности AI — шаблонная сводка с меткой «Без AI».

### US-016. Настройка SLA — FR-030, FR-031
- **AC-052.** Порог 0 или 1441 → ошибка валидации; сохранение 30 → новые лиды получают дедлайн +30 мин, существующие не меняются; запись в аудите.
- **AC-053.** Рабочие часы пн–пт 09:00–18:00, порог 15 мин: лид в пятницу 20:00 → дедлайн понедельник 09:15 по Ташкенту.

### US-017. Импорт CSV — FR-060, FR-061
- **AC-054.** Шаблон скачивается; файл 6 МБ или 5001 строка → отказ с понятной ошибкой; предпросмотр показывает ошибки с номером строки и колонкой.
- **AC-055.** Импорт сохраняет только валидные строки; итог «Импортировано N, пропущено M».
- **AC-056.** Строка с `receivedAt` 10:00 и `firstResponseAt` 10:40 при пороге 15 мин → `BREACHED`; уведомления не созданы; лид учтён в дашборде.
- **AC-057.** Файл в Windows-1251 или с неизвестным разделителем → ошибка «Сохраните файл в UTF-8, разделитель , или ;».

### US-018. API-ключи и intake — FR-062, FR-063
- **AC-058.** Owner создаёт ключ → полный ключ показан один раз; в списке только префикс; 6-й активный ключ → 422 `API_KEY_LIMIT`.
- **AC-059.** Валидный запрос → 201 с `id` и `number`, `createdVia=API`; повтор с тем же `externalId` → 200 с тем же `id`.
- **AC-060.** Неверный/отозванный ключ → 401; 61-й запрос за минуту → 429; невалидное тело → 400 с `details`.

### US-019. Язык и форматы — FR-080, FR-081
- **AC-061.** Переключение RU↔UZ без перезагрузки; после повторного входа язык сохранён; скрипт сверки ключей — 0 пропусков.
- **AC-062.** При таймзоне браузера `Europe/London` дата показывается по Ташкенту в формате `ДД.ММ.ГГГГ ЧЧ:мм`; 12500000 UZS → «12 500 000 сум» / «12 500 000 soʻm».

### US-020. Журнал аудита — FR-090, FR-091
- **AC-063.** Каждое действие из FR-090 создаёт запись с актором, действием, сущностью, временем и IP; owner фильтрует по действию и периоду; head_of_sales и manager → 403.

### US-021. Согласие на внешнюю AI-обработку — FR-009, ADR-016
- **AC-064.** В новой организации AI выключен; owner включает после подтверждения предупреждения; событие в аудите; head_of_sales/manager не видят переключателя, API → 403.

### US-022. Демо-организация — FR-095, FR-096
- **AC-065.** Команда сида создаёт демо-организацию (owner, head_of_sales, 3 менеджера, ≥150 лидов за 30 дней со всеми статусами, источниками и SLA-состояниями); повторный запуск пересоздаёт только её.
- **AC-066.** На всех экранах демо-организации виден незакрываемый баннер «Демо-данные»; в обычной организации баннера нет.

### Сквозные критерии
- **AC-067.** Пользователь организации A, запрашивающий по ID лид, уведомление, участника, приглашение, API-ключ или AI-результат организации B, получает 404; списки не содержат данных B (автотест по всем тенантным эндпоинтам).
- **AC-068.** `GET /api/health` → 200 без авторизации; `GET /api/health/ready` → 200 при доступной БД и 503 при недоступной.
- **AC-069.** E2E-сценарий S-1…S-5 проходит на чистой установке в режиме fallback (без AI-ключа).
