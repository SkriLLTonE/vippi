## ADR-001. Направление продукта
- **Контекст:** у заказчика нет идеи и доступа к отраслям (CONFIRMED). Исследование выделило трёх финалистов: A — контроль заявок, B — документы/ЭСФ, C — операционный контроль смен ([market-research.md](./market-research.md), раздел 1).
- **Решение:** A — AI-контроль заявок и продаж.
- **Обоснование:** деньги на каждой заявке измеримы; ключевые метрики считаются без AI, значит ценность показывается даже без ключа LLM; дешёвый инференс (раздел 2.6 исследования). B требует интеграций с 1С/ЭДО/ЭЦП, у C слабо измеримая польза AI.
- **Последствия:** плотная конкуренция в анализе звонков (ROPai, Reveo, nilu) → позиционирование «все каналы, каждая заявка учтена», а не «оценка звонков».
- **Статус:** CONFIRMED.

## ADR-002. Сегмент для демо
- **Контекст:** доступа к отраслям нет, сегмент выбирается по данным.
- **Решение:** застройщики и агентства недвижимости Ташкента; запасной — автосалоны/дилеры.
- **Обоснование:** высокий чек, рынок тайных покупателей для застройщиков существует (Keyconsulting), компании легко найти через каталоги (urbo.uz, Uysot).
- **Последствия:** AI-извлечение ориентировано на поля недвижимости (бюджет, район, тип объекта, комнаты); при смене сегмента меняются только промпты и справочник полей (`propertyType`, `district` → `carModel` и т.п.). Демо-данные — про недвижимость.
- **Развитие:** с 2026-10-22 недвижимость — один из отраслевых пресетов, а не единственный сегмент (ADR-024).
- **Статус:** PROPOSED → принят в составе концепции.

## ADR-003. Демо-MVP за 7 дней
- **Решение:** узкий, но реальный объём; работающие вычисления, без заглушек; при отставании режем функции по cut-line ([implementation-plan.md](../delivery/implementation-plan.md), раздел 4), а не тесты и не изоляцию тенантов.
- **Утверждённая cut-line (CONFIRMED 2026-10-21, interview-notes Q15):** (1) экран журнала аудита (запись в аудит остаётся); (2) AI-сводка за неделю; (3) настройка рабочих часов SLA; (4) график по дням; (5) шаг предпросмотра импорта CSV; (6) оценка вероятности сделки.
- **Никогда не режется:** изоляция тенантов и её тесты; SLA и уведомления; AI-сводка лида и черновик ответа с fallback; RU/UZ; E2E основных бизнес-сценариев.
- **Приоритет заказчика:** безопасность данных и работающий основной бизнес-процесс — первыми, аналитика и удобство — вторыми.
- **Правило эскалации:** если после снятия всех шести пунктов срок не выдерживается — срок или объём пересогласовываются с заказчиком; обязательные требования не сокращаются.
- **Дополнительные правила (CONFIRMED 2026-10-21, Q18):** безопасность никогда не снижается; режется интерфейс, а не целостность данных (экран аудита можно скрыть, запись событий аудита — нет); функции не удаляются преждевременно — снятие выполняется feature flag'ом/конфигурацией без поломки архитектуры (ADR-020); каждое снятие записывается в раздел «Журнал снятий cut-line» ниже (причина, последствия, условия возврата). Экспорт CSV (ADR-019) и импорт CSV в cut-line не входят; предпросмотр импорта — пункт 5 (Q17).
- **Статус:** CONFIRMED.

## ADR-004. Собственный реестр заявок вместо интеграций с CRM
- **Контекст:** исследование рекомендует продукт как надстройку над amoCRM/Bitrix24/телефонией (раздел 6.1). Интеграции исключены из MVP (CONFIRMED) — за неделю их не сделать качественно, а для демо нужны тестовые аккаунты CRM.
- **Варианты:** (1) интеграция amoCRM в MVP; (2) собственный лёгкий реестр заявок + CSV + intake API; (3) только CSV-аудит без онлайн-режима.
- **Решение (CONFIRMED заказчиком 2026-10-21, Q13):** (2) с **двойным позиционированием**:
  - **(а) «Слой контроля» поверх существующей CRM** — для компаний с amoCRM/Bitrix24: заявки поступают через intake API (вебхук/форма сайта) и импорт CSV-выгрузки; CRM остаётся системой работы со сделками, Vippi Leads — системой контроля реакции. Нативная интеграция amoCRM/Bitrix24 — в roadmap (PRD §28).
  - **(б) Самостоятельный инструмент** — для компаний без CRM (Excel, Telegram-группы): Vippi Leads — единый список заявок с таймером и контролем.
  Intake API и CSV — универсальные точки входа, которые позже станут адаптерами интеграций.
- **Последствия:** в UI нет воронки продаж, сделок, задач — только контроль реакции (иначе сегмент (а) воспримет продукт как конкурента своей CRM). Для сегмента (а) в MVP есть двойной ввод статуса (в CRM и у нас) — честно указывается на демо. После MVP первая интеграция — amoCRM или Telegram Business (по итогам H-06).
- **Статус:** CONFIRMED.

## ADR-005. Модульный монолит
- **Варианты:** микросервисы; модульный монолит; serverless-функции.
- **Решение:** NestJS-монолит с модулями `identity-access`, `organizations`, `leads`, `sla`, `analytics`, `notifications`, `ai`, `audit`.
- **Обоснование:** один разработчик, одна неделя, одна БД; транзакции между лидом, активностью и аудитом — в одной транзакции БД. Микросервисы добавили бы сетевые сбои, распределённые транзакции и отдельный деплой без пользы для демо.
- **Последствия:** границы модулей соблюдаются правилами (только публичные сервисы модуля, свои таблицы — у модуля-владельца; проверка линтером). Выделение сервиса позже — по модулю целиком.
- **Статус:** CONFIRMED.

## ADR-006. Монорепозиторий: pnpm workspaces
- **Варианты:** два отдельных репозитория; npm workspaces; pnpm workspaces; pnpm + Turborepo/Nx.
- **Решение:** pnpm workspaces без Turborepo/Nx. Структура: `apps/web`, `apps/api`, `packages/shared`.
- **Обоснование:** `packages/shared` содержит Zod-схемы запросов/ответов и enum (статусы лида, роли, источники, коды ошибок) — одни и те же правила валидации на форме и в API, исключён рассинхрон контрактов. pnpm строже к фантомным зависимостям и быстрее npm; Turborepo/Nx — лишний слой при двух приложениях (можно добавить позже без переделки).
- **Риск:** NestJS собирается в CommonJS, `shared` — ESM. Смягчение: собирать `shared` через tsup в ESM + CJS (dual package) и проверить в день 1 (T-004).
- **Статус:** PROPOSED.

## ADR-008. ORM: Prisma
- **Варианты:** Prisma, TypeORM, Drizzle.
- **Решение:** Prisma.
- **Обоснование:** декларативная схема и миграции из коробки, типобезопасный клиент, зрелая интеграция с NestJS, быстрый старт. TypeORM — слабее типизация и известные проблемы миграций; Drizzle — ближе к SQL и легче, но меньше готовых паттернов для NestJS и выше стоимость решений «с нуля» за неделю.
- **Последствия:** частичные и trigram-индексы (`pg_trgm`), `percentile_cont` для медианы — через raw SQL-миграции и `$queryRaw` с параметрами (без конкатенации строк). Prisma Client Extension используется для защиты от запросов к тенантным моделям без `organizationId` (ADR-014).
- **Статус:** CONFIRMED (концепция).

## ADR-009. Аутентификация: серверные сессии
- **Варианты:** (1) короткий JWT access (в памяти) + refresh в httpOnly-cookie с ротацией; (2) непрозрачный токен сессии в httpOnly-cookie, хэш токена в БД.
- **Решение:** (2). Cookie `vippi_sid`: `HttpOnly`, `Secure` (вне localhost), `SameSite=Lax`, `Path=/`; срок 7 дней со скользящим продлением; в БД хранится SHA-256 токена. Пароли — argon2id.
- **Обоснование:** web и API отдаются с одного origin (ADR-015), поэтому cookie-сессия проще и безопаснее: мгновенный отзыв при деактивации/смене роли, нет ключей подписи JWT и логики ротации refresh, нет токенов в JS. Цена — один индексированный запрос к БД на запрос API, приемлемо для целевой нагрузки (SPEC, раздел 22). CSRF закрывается `SameSite=Lax` + проверкой заголовка `Origin` на изменяющих запросах.
- **Последствия:** таблица `Session`. Для машинных клиентов — отдельный механизм `X-Api-Key` (только intake). Мобильное приложение в будущем — выдача токенов через отдельный эндпоинт (вне MVP).
- **Статус:** PROPOSED.

## ADR-010. AI: абстракция провайдера и fallback
- **Решение (CONFIRMED заказчиком 2026-10-21, Q14):** интерфейс `AiProvider`; в MVP реализуются **только** адаптер `gemini` (Google Gemini) и `rule_based`. Выбор через `AI_PROVIDER` (`none` | `gemini`) и `GEMINI_API_KEY`. Если ключа нет, организация не дала согласие (ADR-016), превышен лимит, таймаут или ответ не прошёл Zod-валидацию — используется `rule_based`, а результат помечается в UI как «Без AI · по правилам».
- **Обоснование выбора Gemini:** лучший результат на UzLiB среди проверенных (Gemini 3 Flash Preview 0,795 против GPT-5.2 0,662 и Claude Sonnet 4.6 0,641) и низкая цена ([market-research.md](./market-research.md), 2.6). Модель в статусе preview — цена и доступность могут измениться; имя модели задаётся `AI_MODEL`.
- **Вне MVP:** адаптеры OpenAI и Anthropic — добавляются позже через тот же интерфейс без изменения AI-модуля (новый адаптер + значение enum + миграция).
- **Правовое условие:** до обработки реальных данных клиентов — юридическая проверка трансграничной передачи в Google (ст. 27-1 ЗРУ-547 в ред. ЗРУ-1125, перечень ПКМ №415; условие DPF для США проверено только по вторичному источнику). В демо — только синтетические данные.
- **Статус:** CONFIRMED.

## ADR-011. Планировщик вместо очереди
- **Варианты:** `@nestjs/schedule` (cron в процессе API); BullMQ + Redis; pg-boss.
- **Решение:** `@nestjs/schedule`, задача каждую минуту. Идемпотентность: условный `UPDATE ... WHERE slaState='PENDING' AND firstResponseAt IS NULL AND firstResponseDueAt <= now()` + уникальный `dedupeKey` уведомления. Защита от двойного запуска при нескольких экземплярах API — `pg_try_advisory_lock`.
- **Обоснование:** одна задача, допустимая точность ±1 минута, никакой лишней инфраструктуры (Redis). Переход на pg-boss/BullMQ — при появлении внешних интеграций с ретраями.
- **Статус:** CONFIRMED (концепция).

## ADR-012. i18n: i18next
- **Варианты:** i18next + react-i18next; FormatJS (react-intl); Lingui.
- **Решение:** i18next + react-i18next; ICU-плюрализация через `Intl.PluralRules` (встроена в i18next). Форматы дат/денег — через `Intl` с явной таймзоной `Asia/Tashkent`.
- **Обоснование:** самая распространённая экосистема, ленивые namespace, простая проверка полноты ключей в CI. Узбекская латиница — локаль `uz` (`uz-Latn`); кириллица — вне MVP.
- **Статус:** PROPOSED.

## ADR-013. Клиентское состояние
- **Решение:** серверное состояние — только TanStack Query (кэш, refetch, оптимистичные обновления статуса); Zustand — только глобальное UI-состояние: локаль, свёрнутость сайдбара, последние фильтры. Сессия = результат `GET /auth/me` в Query, а не Zustand. Формы — React Hook Form + Zod-схемы из `shared`.
- **Статус:** CONFIRMED (концепция).

## ADR-014. Мультитенантность
- **Варианты:** отдельная БД/схема на тенанта; общая БД + `organizationId` + проверки в приложении; общая БД + Postgres RLS.
- **Решение:** общая БД, `organizationId` в каждой тенантной таблице; `organizationId` берётся **только** из сессии/API-ключа (никогда из тела запроса); все репозитории принимают `organizationId` обязательным параметром; Prisma-extension бросает ошибку, если запрос к тенантной модели не содержит фильтра по `organizationId`; чужой ID → `404 NOT_FOUND`. RLS — PROPOSED после MVP как второй рубеж.
- **Обоснование:** простота и скорость при достаточной защите с автотестами изоляции (SPEC, раздел 21.3).
- **Статус:** PROPOSED.

## ADR-015. Развёртывание
- **Решение:** Docker Compose: `db` (PostgreSQL), `api` (NestJS, при старте `prisma migrate deploy`), `web` (nginx: статика + прокси `/api` → `api`). Один origin → cookie-сессии без CORS. Конфигурация только через env. Для публичного URL — тот же compose на VM с TLS-прокси или PaaS с контейнерами (TBD).
- **Статус:** CONFIRMED (локально); публичный демо-хостинг — ADR-022.

## ADR-016. Согласие на внешнюю AI-обработку
- **Контекст:** текст заявки содержит ПДн клиентов; передача за рубеж требует условий ст. 27-1 ЗРУ-547 (market-research.md, 2.7).
- **Решение:** флаг `Organization.aiExternalProcessingEnabled`: `false` по умолчанию для новых организаций, `true` для демо-организации с синтетическими данными. Включает только владелец, видя предупреждение о передаче данных провайдеру. При `false` — fallback с пометкой.
- **Статус:** PROPOSED.

## ADR-017. Определение «первого ответа»
- **Контекст:** в MVP нет подключения к каналам (ADR-004), поэтому система не видит реальное сообщение клиенту.
- **Решение:** первый ответ = первое зафиксированное менеджером исходящее действие (звонок, в том числе недозвон, или сообщение) через «Отметить первый контакт» или «Отметить черновик как отправленный». Фиксируются время, автор и канал; отменить нельзя; отметка задним числом запрещена в UI (только импорт CSV исторических данных).
- **Последствия:** метрика зависит от честности менеджера (H-07) — это ограничение MVP честно называется на демо и в README. Для пилота — сверка с CRM/телефонией; автоматическое измерение — через интеграции из roadmap (amoCRM/Bitrix24, Telegram Business).
- **Статус:** CONFIRMED (заказчик, 2026-10-21, Q13).

## ADR-018. Доставка уведомлений
- **Варианты:** polling; SSE; WebSocket.
- **Решение:** polling `GET /notifications/unread-count` каждые 30 с (TanStack Query `refetchInterval`, пауза при скрытой вкладке).
- **Обоснование:** задержка ≤30 с приемлема для SLA в минутах; нет sticky-сессий и отдельной инфраструктуры. SSE — после MVP.
- **Статус:** PROPOSED.

## ADR-019. Экспорт лидов в CSV
- **Контекст:** заказчик подтвердил экспорт CSV как обязательную функцию MVP (interview-notes Q16). Нужен для аудита «потерянные заявки», выгрузки в Excel и обратной загрузки в CRM.
- **Решение:** `GET /api/v1/leads/export.csv` принимает те же фильтры, что и список (`status, source, assigneeId, slaState, forgotten, from, to, q, sort`), без пагинации, не более 50 000 строк (`EXPORT_MAX_ROWS`). Права: owner/head_of_sales — все лиды организации, manager — только видимые ему (свои + неназначенные; тот же `visibilityFilter`, что у списка). `organizationId` — только из сессии. Формат: UTF-8 с BOM, разделитель `,`, CRLF, даты `ДД.ММ.ГГГГ ЧЧ:мм` в `Asia/Tashkent`, суммы — целые числа, телефон E.164. Защита от CSV/формульных инъекций: значения, начинающиеся с `=`, `+`, `-`, `@`, табуляции или CR, префиксуются `'`. Заголовки колонок — машиночитаемые имена (совпадают с шаблоном импорта FR-060 там, где поле общее, чтобы выгрузку можно было загрузить обратно), значения enum — коды (`WON`, `INSTAGRAM`…). Каждая выгрузка пишет событие аудита `LEADS_EXPORTED` с `{rows, filters}` (без ПДн клиентов).
- **Последствия:** экспорт не входит в cut-line; e2e-сценарий заканчивается выгрузкой CSV.
- **Статус:** CONFIRMED.

## ADR-020. Cut-line через feature flags и журнал снятий
- **Контекст:** правила заказчика (Q18): снимать не удаляя код, фиксировать каждое снятие.
- **Решение:** 6 опциональных функций управляются флагами (`packages/shared` — `FeatureFlag`: `AUDIT_LOG_UI`, `WEEKLY_SUMMARY`, `BUSINESS_HOURS`, `DAILY_CHART`, `CSV_IMPORT_PREVIEW`, `DEAL_SCORE`). Env `DISABLED_FEATURES` (список через запятую) на API; флаги отдаются фронтенду в `GET /auth/me` (`features`), UI скрывает элемент целиком (без заглушек «скоро»), API соответствующих маршрутов отвечает 404 при выключенном флаге. Данные (например, запись аудита) продолжают записываться независимо от флагов.
- **Статус:** CONFIRMED.

## ADR-021. Решения, принятые при реализации демо-MVP
- **Контекст:** при реализации часть деталей SPEC пришлось уточнить или заменить; фиксируем, чтобы расхождения не были скрытыми.
- **Решения:**
  1. **Версии** — диапазоны в `package.json`, точные версии закреплены в `pnpm-lock.yaml` (`--frozen-lockfile` в Docker): Node 24, pnpm 12, TypeScript 6 (`baseUrl` устарел — пути `./src/*`), React 19, Vite 8 (rolldown), React Router 8, NestJS 11, Prisma 6, Zod 4.
  2. **Rate limiting и валидация** — собственные `RateLimiter` и Zod-pipe на схемах из `packages/shared` вместо `@nestjs/throttler`/`nestjs-zod` (план Б SPEC §3.3: одна схема для API и форм, без адаптеров под Zod 4).
  3. **Интеграционные тесты** — на отдельной PostgreSQL-БД (`DATABASE_URL_TEST`, имя обязано содержать `test`) вместо Testcontainers: тесты не управляют контейнерами и используют тот же PostgreSQL, что и разработка; изоляция — `TRUNCATE` всех таблиц перед каждым тестом.
  4. **Даты и таймзона** — `Intl.DateTimeFormat` с явной `Asia/Tashkent` (без date-fns/tz-библиотек). `computeDueAt` перенесена в `packages/shared`, чтобы превью SLA в настройках считалось той же функцией, что и сервер.
  5. **Таблицы и селекты** — обычные таблицы на токенах design-system (без TanStack Table) и нативные `<select>`: объёмы демо не требуют виртуализации, нативные селекты доступнее на мобильных.
  6. **DEAL_SCORE** — флаг проверяется только в UI (оценка скрывается); API продолжает её вычислять в составе анализа — отдельного маршрута нет, данные не теряются (ADR-020).
  7. **Доля потерянных** на дашборде = `LOST / все лиды периода`.
  8. **axe-core не используется** (лицензия MPL-2.0 не входит в разрешённые MIT/Apache-подобные); доступность проверяется вручную и ролями/лейблами в E2E. Дополнено 2026-10-21: `e2e/responsive-a11y.spec.ts` — собственные автоматические проверки без сторонних движков:
     - снимок доступности Playwright: у каждой интерактивной роли есть имя;
     - контраст WCAG 1.4.3 и размер целей 2.5.8;
     - `lang`, `h1`, `alt`, дубли `id`, горизонтальный скролл на 1440/768/390;
     - клавиатура: skip-link, видимый фокус, возврат фокуса из диалогов.

     Проверки слабее axe по охвату (нет ARIA-валидации атрибутов и landmark-правил) — это осознанное ограничение. Шрифт Inter — SIL OFL 1.1 (шрифт, не код — допустимо).
  9. **Env фронтенда** читается только из `apps/web` (`.env.local`), не из корневого `.env`: корневой `.env` содержит `NODE_ENV=development` для API, и Vite подхватывал его в production-сборку (dev-React, `jsxDEV is not a function`).
  10. **E2E** использует реальный планировщик SLA (cron 1 мин) и SLA = 1 мин, без подмены времени — сценарий ждёт настоящую просрочку (~1–2 мин).
  11. **Docker-порт** настраивается `WEB_PORT`; `PUBLIC_APP_URL` API-контейнера выводится из него (`http://localhost:${WEB_PORT}`) или задаётся `STACK_PUBLIC_URL`; `PUBLIC_APP_URL` из `.env` в стек не попадает — раньше он оставался `:8080` при `WEB_PORT=8081`, и `OriginGuard` отклонял вход.
  12. **Security overrides** в `pnpm-workspace.yaml`: `deepmerge-ts ^8` (через Prisma) и `js-yaml ^5.4.1` (через `@nestjs/swagger`). Остаётся 1 high без патча — `braces` через dev-инструмент `steiger` (линтер FSD, обрабатывает только пути исходников, в рантайм-образы не попадает); пересмотреть при выходе исправления.
  13. **Отклонение от ADR-016:** демо-организация создаётся сидом с `aiExternalProcessingEnabled = false` (ADR-016 предполагал `true`). Ключа Gemini нет, демо идёт в rule-based режиме; при появлении ключа владелец включает согласие в настройках одним переключателем.
- **Статус:** CONFIRMED (исполнитель), требует ознакомления заказчика.

## ADR-022. Публичный демо-стенд на Render (free)
- **Контекст:** заказчик выбрал Render (бесплатный тариф) для публичного URL демо. Сессии — httpOnly cookie, сайт и API на одном origin (ADR-015, SEC-001). Ограничения free-тарифа (по [render.com/docs/free](https://render.com/docs/free), [blueprint-spec](https://render.com/docs/blueprint-spec), [deploys](https://render.com/docs/deploys), проверено 2026-10-21):
  - web-сервис — 512 МБ / 0,1 CPU;
  - засыпает после 15 мин без входящего трафика, просыпается ~1 мин;
  - нет Shell/SSH, one-off jobs и `preDeployCommand` (только платные сервисы);
  - файловая система эфемерная;
  - бесплатная PostgreSQL удаляется через 30 дней после создания (+14 дней льготного периода), без бэкапов, 1 ГБ.
- **Варианты:**
  1. Static Site (web) + web-сервис (api) — два домена `*.onrender.com`. Нужны CORS с credentials и `SameSite=None`, а `onrender.com` в Public Suffix List — cookie стали бы сторонними. Ослабляет модель SPEC.
  2. Один контейнер nginx + node (supervisor). Повторяет compose, но два процесса в 512 МБ и дополнительный слой без пользы.
  3. **Один процесс NestJS отдаёт и API (`/api`), и собранный SPA.**
- **Решение:** вариант 3. Корневой `Dockerfile` собирает shared → web → api; рантайм `node:24-alpine`, non-root, `tini`, `NODE_OPTIONS=--max-old-space-size=256`.
  - **SPA:** при заданном `WEB_DIST_DIR` API отдаёт статику (`apps/api/src/web-static.ts`):
    - `/assets/*` — `immutable`, год кэша; отсутствующий ассет — 404, а не `index.html`;
    - остальные GET вне `/api` → `index.html` с теми же заголовками, что и nginx (CSP, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, `no-cache`);
    - `/api/*` никогда не уходит в fallback (JSON 404).
  - **Origin и cookie:** `PUBLIC_APP_URL` по умолчанию берётся из `RENDER_EXTERNAL_URL`, порт — из `PORT`. `COOKIE_SECURE` по умолчанию `true` при https-origin (в Blueprint задан явно). CORS не включается: один origin, `OriginGuard` без изменений.
  - **IP клиента:** `TRUST_PROXY` — число доверенных прокси-хопов. На Render цепочка «Cloudflare → балансировщик → прокси в инстансе», поэтому `3`: `req.ip` = реальный клиент. Подставной левый элемент `X-Forwarded-For` не обходит лимит входа по IP (интеграционный тест `deployment.test.ts`). Источники: [community.render.com/t/35981](https://community.render.com/t/x-forwarded-for-header-contains-multiple-ips/35981), [arcjet-js#3899](https://github.com/arcjet/arcjet-js/issues/3899). Официальной документации Render по числу хопов нет — значение нужно проверить после первого деплоя (IP входа в журнале аудита = ваш внешний IP; процедура в `deployment.md`).
  - **Миграции:** `prisma migrate deploy` в entrypoint контейнера перед стартом (pre-deploy на free недоступен). Ошибка миграции → контейнер не стартует → health-check не проходит → Render оставляет предыдущую версию.
  - **Демо-сид:** без Shell и one-off jobs. Флаг `DEMO_SEED_ON_START`:
    - `if-missing` (в Blueprint) — создать демо-организацию, если её нет; пробуждения и редеплои данные не трогают;
    - `reset` — пересоздавать на каждом старте (временно, для переналивки);
    - `off` — по умолчанию локально.

    Сбой сида не блокирует старт API. Пароль демо-аккаунтов — `generateValue` в Blueprint. Других секретов у приложения нет: сессии — случайные токены, хэш в БД; пароль БД генерирует Render.
  - **SLA:** cron работает, только пока инстанс не спит. При старте (`onApplicationBootstrap`) выполняется немедленный догоняющий проход. Просрочка считается от сохранённых дедлайнов (`slaBreachedAt = firstResponseDueAt`), идемпотентно (advisory lock, `dedupeKey`). После сна все пропущенные просрочки фиксируются с правильным временем, а уведомления появляются при пробуждении (тест «catch-up after a long sleep»). Таймер в UI считается от дедлайна и корректен всегда.
  - **Прочее:**
    - Swagger выключен;
    - БД доступна только из приватной сети Render (`ipAllowList: []`);
    - автодеплой только после зелёного CI (`autoDeployTrigger: checksPass`).
- **Последствия:**
  - Один образ на ~740 МБ: в нём Prisma CLI и движки для `migrate deploy`.
  - Память в локальном прогоне с лимитом 512 МБ / 0,1 CPU — пик 102 МиБ (`deployment.md`).
  - Лимиты частоты запросов — в памяти процесса, сбрасываются при перезапуске/сне (допустимо для одного инстанса).
  - БД нужно пересоздавать раз в 30 дней — это демо-стенд, не пилот. Для реальных данных — платная БД с бэкапами и юридическая проверка (H-12, TBD-6).
  - Compose-стек (ADR-015) не меняется: `docker-entrypoint.sh` общий, по умолчанию `DEMO_SEED_ON_START=off`.
- **Статус:** CONFIRMED (исполнитель, 2026-10-21); число прокси-хопов — проверить на первом деплое.

## ADR-023. Web Push и email-уведомления
- **Контекст:** колокольчик (ADR-018) виден, только пока вкладка открыта. Заказчик выбрал два внешних канала: уведомления браузера (Web Push) и email. Уведомления создаются внутри бизнес-транзакций (планировщик SLA под advisory lock, назначение лида). Сетевые вызовы внутри транзакции недопустимы: они держат блокировки и могут отправить сообщение об откаченной записи.
- **Решение:**
  - **Outbox.** `Notification.dispatchedAt` (null = ждёт отправки). `NotificationDispatcherService` раз в 15 с под `pg_try_advisory_xact_lock(7_242_002)` забирает до 100 строк и проставляет `dispatchedAt`, а после коммита отправляет.
    - Доставка at-most-once: ошибка отправки пишется в лог (только коды, без адресов), повторов нет. Источник истины — запись в приложении.
    - Уведомления старше 6 ч (например, если free-инстанс спал) помечаются, но не отправляются.
    - Миграция и демо-сид помечают существующие строки отправленными: ретроактивной рассылки нет.
  - **Web Push** — стандарт VAPID, библиотека `web-push` (MIT), без Firebase и внешних аккаунтов.
    - Подписки хранятся в `PushSubscription` (тенантная модель): по одной на браузер, не больше 10 на пользователя.
    - Повторная подписка того же endpoint из другого аккаунта переносит его: общий компьютер не получает чужие уведомления.
    - Ответ 404/410 от push-сервиса удаляет подписку.
    - **SSRF:** сервер шлёт POST на endpoint из браузера, поэтому принимаются только `https://` без порта и userinfo на хостах push-сервисов: `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `*.notify.windows.com`, `web.push.apple.com`.
    - `apps/web/public/sw.js`: только `push` и `notificationclick`, без кэша и fetch-обработчика. Открывает лишь адреса своего origin. CSP не меняется: worker с того же origin разрешён `script-src 'self'`.
  - **Email** — любой SMTP через `nodemailer` (MIT-0): Gmail с паролем приложения, Яндекс, Resend, SendGrid и т. п.
    - Включается самим пользователем в профиле (opt-in, `User.emailNotificationsEnabled`).
    - Демо-организациям письма не отправляются: адреса вымышленные.
  - **Содержимое (FR-040, NFR-016):** номер лида, тип события, имя сотрудника, назначившего лид, и ссылка `PUBLIC_APP_URL/leads/:id`. ПДн клиента и текст обращения не передаются. Язык — `User.locale` (RU/UZ). В письме есть ссылка на отключение (профиль).
  - **Конфигурация:** `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT`, `SMTP_*`, `NOTIFY_DISPATCH_ENABLED`. Пустые значения выключают канал: UI объясняет, что канал не настроен, а API отвечает 422 на попытку включить.
  - **API:**
    - `GET/PATCH /notifications/settings`;
    - `POST /notifications/push-subscriptions` и `/push-subscriptions/remove`;
    - `POST /notifications/test` — тестовая отправка, не больше 5 раз за 10 мин.
- **Последствия:**
  - Push приходит, пока запущен браузер. На iOS нужен установленный PWA (манифеста пока нет) — iPhone в MVP не поддерживается.
  - Задержка доставки — до 15 с поверх события (cron SLA — 1 мин).
  - Без повторов письмо может потеряться при сбое SMTP. Это допустимо, потому что уведомление остаётся в колокольчике.
  - На каждую просрочку уходит отдельное письмо. Если писем станет слишком много, следующий шаг — дайджест.
- **Статус:** CONFIRMED (заказчик выбрал Web Push и email, 2026-10-21).

## ADR-024. Любая лидогенерация: пресеты, свои поля, названия статусов
- **Контекст:** ADR-002 выбрал недвижимость как сегмент для демо и предусмотрел смену сегмента «только промптами и справочником полей». Ядро продукта — таймер первого ответа, просрочки, уведомления, дашборд — от отрасли не зависит. Заявки в клиники, учебные центры, автосалоны и сервисные компании проходят тот же путь, но поля `district`/`propertyType`/`rooms` и вопросы AI про комнаты им не подходят. Позиционирование ADR-004 (слой контроля над CRM, а не CRM) сохраняется.
- **Варианты:**
  1. Отдельная сборка или форк на каждую отрасль.
  2. Конструктор воронок, сделок и полей, то есть полноценная CRM.
  3. Отраслевой пресет плюс ограниченный набор своих полей и названий итоговых статусов.
- **Решение (CONFIRMED заказчиком 2026-10-22):** вариант 3.
  - **Пресет.** `Organization.industryPreset`: `REAL_ESTATE` (по умолчанию, все существующие организации) или `GENERIC`.
    - Выбирается при регистрации. Владелец может переключить его в настройках компании; переключение пишется в аудит (`ORG_INDUSTRY_PRESET_CHANGED`).
    - Колонки недвижимости (`district`, `propertyType`, `rooms`, `budget*`) остаются в схеме и данных. В `GENERIC` поля недвижимости скрыты в формах, карточке и кнопках «Применить» AI. Бюджет виден всегда.
    - Переключение ничего не стирает: данные только скрываются или снова показываются. Веб-форма в `GENERIC` не отправляет скрытые поля.
  - **AI.** В `GENERIC` используются отдельные промпты `lead-analysis-generic@1` и `reply-draft-generic@1`; промпты недвижимости не меняются, поэтому кэш их результатов остаётся валидным.
    - Rule-based fallback не задаёт вопросов о районе и комнатах, не начисляет за них баллы и возвращает эти поля как `null`. Из AI применяется только бюджет.
    - Названия своих полей передаются модели в блоке `<business_fields>`, чтобы она спрашивала о незаполненных.
  - **Свои поля лида.** До 8 определений на организацию хранятся в `Organization.leadFieldDefs` (JSON).
    - Каждое определение: `key`, подпись ru/uz, тип `text | number | money | single_select` (с вариантами), `required`, `showInCreate`.
    - Управляют владелец и РОП (`leadFields.manage`), изменения пишутся в аудит (`LEAD_FIELDS_UPDATED`). Ключ и тип после создания не меняются, чтобы сохранённые значения оставались валидными.
  - **Значения своих полей.** Хранятся в `Lead.attributes` (JSONB).
    - Сервер проверяет их схемой Zod, которая строится по определениям организации. Неизвестные ключи отклоняются (`unknown_field`), поэтому определения одной организации не применяются к другой.
    - `required` проверяется только при ручном создании и редактировании; intake API и CSV его не требуют, чтобы не терять входящие заявки.
    - Удаление определения скрывает значения, но не стирает их: если создать поле с тем же ключом, значения вернутся.
    - В экспорте CSV фиксированные колонки сохраняются, после них добавляются `attr:<key>`. Импорт CSV своих полей не читает.
  - **Названия итоговых статусов.** `Organization.statusLabels` — необязательные ru/uz-названия для `WON`/`LOST` (например, «Записан» / «Не записался»); меняет их владелец.
    - Коды статусов, переходы, аналитика и API не меняются.
    - Веб подставляет названия через ресурсы i18next, поэтому они видны везде, где показывается статус: списки, карточка, фильтры, дашборд, «Моя статистика».
- **Почему JSON, а не таблицы:** определений не больше 8, они читаются вместе с организацией, сами определения не фильтруются, а значения валидируются в приложении. Отдельные таблицы EAV усложнили бы каждый запрос лидов ради возможностей, которые мы сознательно не делаем.
- **Чего мы не делаем:**
  - Конструктор воронки и своих статусов: статусная машина `NEW → CONTACTED → QUALIFIED → WON/LOST` остаётся фиксированной.
  - Сделки, задачи и товары (ADR-004).
  - Международные телефоны: остаются только +998.
  - Переименование слова «лид».
  - Фильтры и поиск по своим полям.
  - Импорт своих полей из CSV.
- **Последствия:**
  - Новые организации любой отрасли работают без доработок.
  - Демо-сид содержит вторую организацию «Demo Smile Dental (DEMO)» на пресете `GENERIC` с полями «Услуга» и «Удобное время»; «Demo Realty» остаётся `REAL_ESTATE`.
  - Спецификация — [SPEC-multi-industry.md](../technical/SPEC-multi-industry.md). Миграция `20261022090000_industry_presets` только добавляет колонки со значениями по умолчанию.
- **Статус:** CONFIRMED (решения заказчика 2026-10-22: страна, фиксированные статусы, судьба колонок недвижимости, переключение пресета, демо).

## ADR-025. Каталог отраслевых шаблонов: выбор отрасли настраивает компанию
- **Контекст:** после ADR-024 у «Другого бизнеса» пустой список полей, и владелец должен сам придумать «Услугу» или «Курс». Заказчик (2026-10-23): платформа должна подстраиваться под тип бизнеса, поля лида должны заполняться автоматически по отрасли, а не только данные о квартирах. Примеры в интерфейсе (пример запроса на странице API-ключей) были захардкожены под недвижимость.
- **Варианты хранения отрасли:**
  1. Расширить enum `IndustryPreset` десятком значений. Каждая новая отрасль — миграция `ALTER TYPE`; все проверки `industryPreset === 'GENERIC'` в API, AI и вебе пришлось бы переписать.
  2. Отдельная колонка `Organization.industry` — строковый код из каталога в `@vippi/shared`, а `industryPreset` остаётся флагом поведения (колонки недвижимости и промпты недвижимости) и вычисляется из отрасли при записи.
- **Решение:** вариант 2.
  - **Каталог** `packages/shared/src/industries.ts` (`INDUSTRY_CATALOG_VERSION = 1`): чистые данные, общие для API и веба. 11 кодов под малый бизнес Узбекистана: `REAL_ESTATE`, `DENTAL_CLINIC`, `MEDICAL_CLINIC`, `BEAUTY_SALON`, `EDUCATION`, `AUTO`, `CONSTRUCTION_RENOVATION`, `TOURISM`, `B2B_SERVICES`, `RETAIL_ECOMMERCE`, `OTHER`.
    - Шаблон: название ru/uz; 3–4 поля (`LeadFieldDef`, ключи camelCase как в ADR-024, все необязательные, чтобы не ломать ручное создание); названия `WON`/`LOST` ru/uz; пример заявки ru/uz и пример атрибутов (валиден по своим полям); подсказка для AI на английском (название отрасли + что уточнять); пресет.
    - `REAL_ESTATE` полей не добавляет: у него встроенные колонки, его поведение и промпты не меняются. `OTHER` — без полей и названий (это прежний `GENERIC`).
    - Целостность каталога проверяют unit-тесты: схема полей, ≤ 8 (фактически ≤ 6), уникальные ключи, подписи ru/uz, пример валиден.
  - **Миграция** `20261023090000_org_industry` (аддитивная): `industry VARCHAR(32) NOT NULL DEFAULT 'REAL_ESTATE'` (совпадает с умолчанием пресета); существующие `GENERIC` → `OTHER`; синтетическая «Demo Smile Dental (DEMO)» → `DENTAL_CLINIC` (её ключи полей совпадают с шаблоном). Колонки не удаляются.
  - **Чтение** (`resolveIndustry`): если код неизвестен или противоречит пресету, отрасль выводится из пресета (`REAL_ESTATE` или `OTHER`). Пресет остаётся источником истины для поведения.
  - **Регистрация:** `industry` (приоритетнее устаревшего `industryPreset`) создаёт организацию с полями и названиями итогов шаблона. Без обоих полей — `REAL_ESTATE`, как раньше. `industryPreset: GENERIC` → `OTHER`.
  - **Смена отрасли** (только владелец, `org.manage`):
    - `PATCH /organization { industry }` меняет только отрасль (и вычисляемый пресет), поля не трогает. Устаревший `industryPreset` по-прежнему принимается: `GENERIC` сохраняет конкретную не-недвижимостную отрасль, иначе даёт `OTHER`.
    - `POST /organization/industry-template { industry, overwriteStatusLabels? }` меняет отрасль и **сливает** шаблон: добавляет недостающие поля (сравнение ключей без учёта регистра) до лимита 8, не удаляет и не меняет существующие определения и значения `Lead.attributes`; пустые названия итогов заполняет, свои — заменяет только при `overwriteStatusLabels: true`. Под блокировкой строки организации, как правки полей.
    - Превью в вебе и применение на сервере используют одну чистую функцию `planIndustryTemplate`, поэтому показанное совпадает с выполненным.
    - Аудит: `ORG_INDUSTRY_CHANGED {from,to}` (коды отраслей), `ORG_INDUSTRY_PRESET_CHANGED {from,to}` (если сменился пресет, как в ADR-024), `ORG_INDUSTRY_TEMPLATE_APPLIED {industry, catalogVersion, addedFields, skippedFields, statusLabelsChanged}`.
  - **Где используется отрасль:** выбор при регистрации (список + «что будет настроено»); пример запроса на странице API-ключей (текст заявки отрасли и реальные ключи полей организации; если значение примера не подходит к изменённому полю — типовой заполнитель); подсказки в форме лида (текст заявки, текстовые поля); универсальные AI-промпты получают название отрасли и подсказку — версии подняты до `lead-analysis-generic@2` и `reply-draft-generic@2`, код отрасли входит в хэш кэша. Промпты недвижимости не менялись.
- **Чего мы не делаем:** отдельная отрасль «Фитнес» (пока `OTHER` + свои поля; добавить — одна запись в каталоге без миграции); автоматическое удаление полей прежней отрасли; локализация каталога вне ru/uz; обязательные поля в шаблонах.
- **Допущения исполнителя (заказчик не был на связи):** в форме регистрации по умолчанию по-прежнему выбрана «Недвижимость» (не ломает e2e и прежнее поведение API); стоматология и медицинская клиника — разные шаблоны; поле «Услуга» демо-клиники стало необязательным, как во всех шаблонах.
- **Последствия:** новая отрасль — правка каталога и версии без миграции; спецификация — [SPEC-multi-industry.md](../technical/SPEC-multi-industry.md#каталог-отраслей-adr-025).
- **Статус:** PROPOSED (реализовано, ждёт подтверждения заказчика; расширяет ADR-024).
